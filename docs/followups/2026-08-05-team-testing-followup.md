# 内容审核 Agent 组内试用 Follow-up

日期：2026-08-05

## 结论摘要

建议继续开发，但不要按“全自动审核员”方向承诺价值。更稳妥的定位是：

> 面向内部内容审核的 AI 辅助工作台：批量预审、五维度风险提示、人工复核分流、供应商问题沉淀。

这轮组内测试证明系统已经具备可演示价值：多人登录、上传 Excel、按批次审核、生成维度评分、输出人工任务和发布状态都能跑通。但它离稳定给团队日常使用还有明显差距，核心问题集中在部署可靠性、模型配置容错、导入校验、审核状态解释和任务交互。

如果后续资源有限，建议先做 1-2 周“可用性加固”，不要马上扩展新功能。加固后再判断是否进入正式迭代。

## 本轮试用观察

### 已跑通的能力

- 团队账号可以登录，成员账号互相隔离。
- 每个成员可以保存自己的 One API key，key 加密保存且不回显明文。
- Excel 批量导入可以生成批次和内容表。
- 批量审核可以调用 OneAPI，并为稿件生成五维度结果。
- 审核后能给出状态分流：已通过、需人工确认、需内容修改、暂不可发布。
- 审核台可以查看内容、评分维度、问题和人工任务。

### 实测数据快照

截至本次复盘，本地数据库里最近两个真实组内测试批次为：

| 批次 | 上传人 | 内容数 | 通过 | 需修改 | 需人工确认 | 格式不完整 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 2026-暑期-01 | jhz | 5 | 0 | 0 | 4 | 1 |
| 02 | lyx | 20 | 3 | 7 | 10 | 0 |

批次 `02` 使用 `gpt-5.6-luna` 完成 20 条审核，耗时约 639 秒。说明现有方案能跑真实批量任务，但速度、反馈和状态解释仍需要优化。

## 用户反馈对应的问题

### 1. 登录和服务访问不稳定

现象：

- 同事访问 `http://172.21.213.223:5173/` 时一度打不开。
- 管理员/团队密码曾因特殊字符和服务重启状态造成误解。

原因：

- 当前是本地开发服务，不是正式部署。电脑关机、终端停止、网络切换、VPN 或局域网隔离都会导致同事打不开。
- 局域网 IP 依赖当前网络，今天可用不代表明天可用。

影响：

- 研讨会演示或组内测试容易被“服务没开”打断。
- 非技术同事会把网络/启动问题理解成产品不可用。

建议：

- 若继续试用，应部署到固定内网地址或云服务，避免依赖个人电脑。
- 登录页增加“服务状态/后端不可达”的明确提示。
- 准备一页团队账号说明，包含地址、账号、初始密码、API key 填写步骤和常见错误。

### 2. 模型配置踩坑导致“没有结果”

现象：

- 同事发起审核后，页面显示“模型审核不可用，需要人工审核”，评分为空。

根因：

- 原默认模型 `GPT 5.6 SOL` 调 OneAPI 返回 `HTTP 503 type=one_api_error`。
- 换成 `gpt-5.6-luna` 后，同一类审核可以正常返回结果。

已经处理：

- 前端默认模型改为 `gpt-5.6-luna`。
- 后端团队默认模型改为 `gpt-5.6-luna`。
- 前端模型候选中移除了 `GPT 5.6 SOL`。
- README 的团队配置示例已同步。

仍需优化：

- 保存模型配置时应主动做一次轻量连通性测试，而不是等审核时才失败。
- OneAPI 失败时应展示可理解原因，例如“模型不可用/网关 503/请检查模型名”，而不是只生成系统类审核结果。
- 管理员需要能看到团队成员是否已配置 key、模型是否验证通过。

### 3. API key 保存成功但用户不确定是否生效

现象：

- 成员粘贴 key 后，输入框清空，只看到“已保存”，容易怀疑没有保存。
- 顶部模型状态有时需要刷新页面后才同步。

原因：

- 出于安全考虑，key 不回显是正确的。
- 但当前“已保存”的反馈不够强，没有告诉用户下一步该做什么。

建议：

- 卡片显示更明确的状态：`Key 已保存 / 模型已验证 / 上次验证时间`。
- 保存成功后文案改为“已保存，后续审核将使用你的个人 key”。
- 顶部状态保存后立即刷新，不依赖用户手动刷新。

### 4. Excel 导入校验不够前置

现象：

- `2026-暑期-01` 的 Excel 第 5 行标题为空，被系统标为 `INCOMPLETE`，未进入自动审核。
- 用户容易理解成“系统没审这条”或“点击没反应”。

原因：

- 导入时允许不完整行进入内容表，但前端没有足够突出地解释“为什么未审核”。

建议：

- 上传预览阶段就标红必填字段缺失，并要求用户确认是否跳过。
- 内容表增加“未审核原因”列或 hover 说明。
- 批次进度里把“跳过”拆成：格式不完整、已有结果无需重复审核、系统跳过。

### 5. 任务表和详情交互不清晰

现象：

- 同事点击任务列或某些区域“没有反应”。
- 任务列只显示“1 个开放任务”，看不出具体要改什么。

原因：

- 原本只有“内容/版本”里的文字按钮能选中行。
- 任务列本身不是操作入口，缺少明确视觉提示。
- 系统类问题、人工任务、供应商修改任务混在一起，用户不容易理解下一步动作。

已经处理：

- 审核台内容表已改成整行可点击。
- 鼠标 hover 和键盘 Enter/空格选择已支持。

建议：

- 任务列显示任务类型摘要，例如“需人工确认：产品准确性”“需修改：合规表达”。
- 行点击后自动滚动到下方详情，减少用户找不到详情区域的问题。
- 对 `SYSTEM-LLM-UNAVAILABLE` 这类系统问题，在任务表中单独标识为“系统异常”，不要和内容风险混为一谈。

### 6. 重复点击“开始审核”会产生误解

现象：

- 批次 `02` 完成后，又出现两次审核任务记录：`completed_count=0, skipped_count=20`。
- 用户看到任务完成，但不知道其实 20 条全部被跳过。

原因：

- 已有有效审核结果时，系统会跳过重复审核。
- 前端没有明确提示“该批次已审核完成，重新审核需要手动选择强制重审”。

建议：

- 批次已完成后，把按钮从“开始审核”改为“重新审核全部”，并弹确认说明。
- 进度面板显示跳过原因分布。
- 增加“只审核未审核/失败/格式修复后内容”的模式选择。

## 产品价值判断

### 值得继续的信号

- 它解决的是团队真实痛点：批量内容预审、统一审核口径、减少人工初筛压力。
- 多人账号、个人 key、批次隔离这些底座已经初步具备。
- 对 Excel 批量稿件，系统能输出可执行的分流结果。
- 审核标准和项目 brief 可以沉淀，适合后续形成供应商问题库。

### 暂不适合承诺的方向

- 不适合承诺“自动给最终发布结论”。当前大量稿件仍会进入人工确认或供应商修改。
- 不适合马上面向大范围团队开放。服务部署和错误提示还不够稳定。
- 不适合继续堆新维度或新模型，当前瓶颈不是维度数量，而是可靠性和解释性。

## 建议路线

### 推荐方向：继续开发，但收敛为“审核辅助 + 问题沉淀”

下一阶段目标不是让 AI 替代审核，而是让审核人更快定位：

- 哪些稿件可以低风险通过；
- 哪些稿件需要供应商修改；
- 哪些问题高频出现；
- 哪些规则、brief 或素材证据需要补充。

这个方向更容易向老板解释价值，也更符合当前系统能力边界。

### 两周优先级

P0：稳定试用环境

- 部署到固定地址。
- 配置持久数据库和固定 SESSION_SECRET。
- 管理员页展示成员 key/model 配置状态。
- 保留测试账号和试用说明。

P1：减少“没结果”的误解

- 保存模型时做 OneAPI 连通性验证。
- 模型不可用时在前端显示真实可理解错误。
- 批次进度显示跳过原因。
- 导入预览强提示必填字段缺失。

P2：让审核结果更可用

- 任务列展示具体维度和修改类型。
- 点击行后自动定位到详情。
- 报告页增加“供应商高频问题沉淀”和“可复用修改建议”。
- 导出可直接给供应商的修改清单。

## 是否转向的判断标准

建议再做一轮小规模验证后决策。可以设置以下门槛：

- 5 个成员都能独立完成：登录、配置 key、上传、审核、查看详情。
- 3 个真实批次、至少 50 条稿件完成审核。
- 90% 以上稿件能得到非系统异常的维度结果。
- 用户能在不问开发者的情况下理解“为什么这条需要修改/人工确认”。
- 审核人认为它节省了至少 30% 初筛时间。

如果达不到上述门槛，建议不要继续做成“大而全审核平台”，而是转向更轻的工具：

- Excel/报告生成器；
- 供应商问题沉淀助手；
- 审核标准问答和规则检索助手；
- 单篇稿件批注插件。

## 下一次汇报建议表达

可以这样对老板汇报：

> 这次组内试用验证了方向有价值：工具能完成批量导入、AI 五维预审、任务分流和问题沉淀。但它目前还不是稳定生产系统，主要问题在模型配置、部署稳定性和结果解释。我们建议继续投入一个短周期，把它从 Demo 打磨成内部可试用 MVP；下一阶段不追求更多功能，而是追求可登录、可审核、可解释、可复盘。
