# 内容审核 Agent 组内试用 Follow-up 报告

日期：2026-08-05  
项目：百度地图内容审核台 / 内容审核 Agent  
场景：AI 研讨会项目后续评估  

## 1. 背景

我们小组在 AI 研讨会中提交了“内容审核 Agent”项目，希望用 AI 辅助完成供应商稿件的预审、风险识别和问题沉淀。项目已经做出可试用版本，支持团队成员登录、上传 Excel、批量审核、查看五维评审结果，并生成需要人工确认或供应商修改的任务。

这次 follow-up 的重点不是证明 Demo 能跑，而是基于组内真实试用反馈，判断这个方向是否值得继续投入。

经过组内试用后，我们的判断是：这个项目可以证明 AI 在基础检查上有一定价值，但不建议继续把它作为独立审核平台开发。后续更值得探索的方向，是把 AI 用在竞品分析报告这类信息整理、结构化分析和洞察输出任务上。

## 2. 当前结论

不建议继续开发内容审核 Agent 平台。

原因不是这个 Demo 完全没有价值，而是它的价值边界比较清楚：用于基础检查、格式问题识别、明显风险提示是可以的；但如果把它定位成审核辅助系统，期望它稳定理解平台语感、产品细节、合规边界和具体活动上下文，目前模型能力和维护成本都不太匹配。

更直接地说，这个项目适合做成一次 AI 研讨会 Demo，证明 AI 可以辅助处理一部分重复检查工作；但不适合继续投入成一个长期使用的审核产品。

后续建议转向：

> 用 AI 辅助生成竞品分析报告，重点做竞品信息收集、功能对比、内容策略拆解、用户反馈归纳和机会点总结。

这个方向比内容审核更适合现阶段模型能力。竞品分析本身需要大量阅读、归纳、对比和结构化输出，对确定性要求没有审核结论那么高，也更容易通过人工复核保证质量。

## 3. 本轮试用结果概览

已经跑通的能力：

- 团队成员可以登录系统。
- 成员可以填写自己的 One API key 和模型配置。
- 可以上传 Excel 稿件并生成批次。
- 可以对批次进行 AI 审核。
- 审核后可以看到五个维度的结果：基础内容校对、合规审核、品牌一致性、产品准确性、传播有效性。
- 系统会给出发布状态，例如通过、需要人工确认、需要修改、暂不可发布。
- 内容表中可以看到每条稿件的状态、风险和任务数量。

组内测试中暴露的问题也比较集中：

- 有同事访问本地服务时打不开。
- 有同事配置模型后没有拿到有效审核结果。
- API key 保存后，用户不确定是否真的生效。
- 有些 Excel 行因为标题为空或字段不完整，没有进入自动审核。
- 内容表里的“任务”列不够直观，用户不知道点哪里，也看不出具体要做什么。
- 审核规则对小红书标题党和口语化表达过于敏感。
- 产品功能事实库不完整，导致实际支持的能力被误判为需要人工确认。

这些问题里，有些是工程体验问题，可以通过继续开发解决；但更核心的是模型判断边界问题。内容审核需要非常稳定的事实理解和风险判断，而现阶段模型在这些地方仍然容易出现误判。

## 4. 关键反馈与问题分析

### 4.1 审核条件偏死板，标题党表达被误判为风险

同事反馈：

> 一些问题其实只是标题党，为了吸引人眼球，但系统都算成了风险项。

典型例子：

- “现在出去玩儿再也不用费劲做攻略了”
- “下次追范丞丞线下再也不用做攻略了！”
- “怀疑小度想想在我脑子里装了监控”

这些表达在小红书、KOC 种草内容里很常见，很多时候是为了制造标题吸引力，并不一定是在做严格的产品承诺。比如“再也不用做攻略”如果正文只是描述一次厦门出游体验，那么它更像是个人体验的夸张表达，而不是“产品永久解决所有攻略问题”的承诺。

目前系统的问题是，它对“再也不用”“搞定所有”“监控”等词比较敏感，容易直接触发中风险判断。这样会带来两个后果：

- 误报偏多，审核人需要花时间解释“这其实只是标题党”。
- 供应商会觉得系统太机械，不符合平台内容语感。

这类问题可以通过补规则、补样例缓解，但很难彻底消除。因为内容审核不是单纯的关键词判断，它依赖平台语境、品牌口径、活动背景和人工经验。模型可以给提醒，但很难稳定替代审核人的判断。

### 4.2 产品功能理解不够，实际支持的能力被转人工复审

同事反馈：

> 实际拥有的内容，审核觉得不能实现，需要人工复审。是不是可以加一个产品功能点的东西进去？这种小事儿可以直接审核，不需要再耗费人力。

典型例子：

- 稿件里写“直接帮我打个车吧”，系统判断为打车完整交互流程缺少已批准事实支持。
- 稿件里写“能切换同款语音”，系统判断为该语音能力不在已批准产品事实中。

这个问题不是模型完全不能判断，而是它需要一个非常完整、持续更新的产品事实库。只要事实库里没有写清楚某个能力，模型就会倾向于保守处理，把它转成人工确认。

如果继续做审核平台，就必须长期维护：

- 产品功能白名单；
- 产品功能灰名单；
- 禁用表达口径；
- 活动授权范围；
- 不同批次的 brief；
- 供应商可说和不可说的边界。

这会让项目从一个轻量 AI 工具变成一个需要持续运营的审核知识库。对当前小组来说，投入产出比不高。

### 4.3 团队试用门槛偏高

这次试用中，登录、访问地址、API key、模型配置都出现过问题。对于开发者来说，这些问题可以通过看日志和改配置解决；但对于团队成员来说，它们就是“系统不好用”。

目前比较明显的问题：

- 本地服务依赖个人电脑和局域网 IP，同事不一定能稳定访问。
- API key 保存后不回显是安全的，但用户不知道是否生效。
- 模型不可用时，前端给出的解释不够直接。
- 如果 OneAPI 返回 503，用户看到的结果更像“审核失败”，但不知道原因是模型不可用。

这些问题继续开发可以解决，但它们会进一步增加部署、权限、账号和运维成本。考虑到核心审核判断并不稳定，继续投入工程化并不划算。

### 4.4 审核结果可解释性还不够

同事反馈中提到，任务表看不出修改情况，点击刚导入的内容也没有明显反应。这说明当前界面虽然有数据，但信息层级还不够清楚。

目前的问题：

- “1 个开放任务”太抽象，不知道是合规问题、产品问题还是文案建议。
- 点击区域不明确，用户不知道哪里可以看详情。
- 有些结果显示“需要人工确认”，但没有足够解释为什么必须人工确认。
- 系统异常、内容风险、产品事实缺失混在一起，容易造成误解。

即使把界面优化好，审核结果本身仍然需要人判断。对于内容审核来说，如果系统不能稳定给出可信结论，它的辅助价值就会打折。

## 5. 是否继续开发：判断

不建议继续开发。

原因有三点。

第一，模型适合做基础检查，但不适合承担较重的审核判断。  
它能发现格式缺失、明显风险词、表达过度、信息不完整等问题；但面对标题党、平台语感、产品功能边界、活动授权口径时，误报和保守判断都会比较多。

第二，审核平台需要长期维护知识库。  
如果要让它真正可用，就要不断更新产品事实、合规规则、活动 brief、品牌口径和供应商样例。这个维护成本不低，而且只要维护不到位，模型就会继续把很多内容转人工。

第三，继续产品化的收益不够明确。  
当前系统能节省一部分基础检查时间，但为了达到团队日常可用，需要继续投入部署、账号、权限、错误提示、结果解释、报告导出等工程工作。考虑到模型判断仍有限，这个投入不一定值得。

因此，这个项目更适合作为研讨会 Demo 和内部试验沉淀，而不是继续做成正式工具。

## 6. 后续方向：转向竞品分析报告

我们现在更建议把 AI 探索方向转到竞品分析报告。

相比内容审核，竞品分析更适合模型发挥，因为它的核心任务是：

- 收集和整理公开信息；
- 对比不同产品的功能和表达；
- 归纳内容策略和传播打法；
- 总结用户反馈中的高频需求；
- 提炼机会点和可借鉴做法；
- 输出结构化报告。

这些任务对模型更友好。即使模型有遗漏或判断不够准，也可以通过人工复核、补充数据源和调整报告结构来修正。它不像内容审核那样，每一个结论都可能直接影响稿件是否能发布。

换句话说，竞品分析允许 AI 做“初稿和信息整理”，人来做“判断和取舍”；而内容审核更容易让 AI 直接进入“判定”环节，风险更高。

## 7. 竞品分析报告可以怎么做

建议下一阶段先做一个轻量版本，不急着做平台。

可以先用固定报告模板跑一轮，例如：

### 7.1 报告结构

- 竞品基本信息：产品定位、核心用户、主要场景。
- 核心功能对比：导航、出行规划、AI 助手、语音交互、打车、路线推荐等。
- 内容与营销打法：小红书、抖音、公众号、应用商店等渠道的表达方式。
- 用户反馈归纳：好评点、差评点、高频需求、典型抱怨。
- 功能机会点：竞品已经做了什么，我们可以借鉴什么。
- 内容机会点：哪些表达方式适合后续种草或 campaign。
- 风险提醒：哪些结论数据不足，需要人工确认。

### 7.2 首轮可选竞品

可以先选 3-5 个和百度地图相关度高的对象：

- 高德地图；
- 腾讯地图；
- Apple 地图；
- 携程 / 飞猪的旅行规划能力；
- 小红书里的出行攻略内容生态；
- 具备 AI 出行助手能力的新产品或插件。

不一定一开始就覆盖很多竞品。第一轮更重要的是验证报告是否有用。

### 7.3 交付形式

建议先输出 Markdown 或 PPT 版报告，不急着做系统页面。

每份报告重点回答三个问题：

- 竞品在做什么？
- 用户为什么买账或不买账？
- 对我们当前产品和内容策略有什么启发？

如果报告真的被团队使用，再考虑把流程产品化。

## 8. 下一步建议

建议把后续工作拆成两步。

第一步，停止继续开发内容审核 Agent 平台。保留现有 Demo、代码和试用结论，作为研讨会项目成果和经验沉淀。

第二步，用 1 周时间做一份竞品分析报告样稿。先不要开发新系统，直接验证 AI 是否能帮助团队更快完成竞品信息整理和洞察输出。

样稿建议聚焦一个具体问题，例如：

> AI 出行助手在地图和旅行产品中的竞品机会分析。

这个题目和当前项目仍然有关联，也更容易承接老板对 AI 应用价值的期待。

## 9. 给老板汇报时可以这样说

这次组内试用验证了内容审核 Agent 的基础价值：AI 可以帮助做格式检查、明显风险提示和初步问题归类。但试用后我们也看到，它不适合继续作为审核平台投入。

主要原因是内容审核需要非常强的语境理解和产品事实判断。比如小红书标题党、活动授权能力、产品功能边界，这些都不是模型仅靠通用能力就能稳定判断的。如果要继续做，需要长期维护规则和产品事实库，投入成本会比较高。

所以我们的建议是：内容审核 Agent 到 Demo 验证阶段即可，不继续产品化。后续把探索方向转到竞品分析报告。这个方向更适合模型做信息整理、归纳对比和初稿输出，也更容易通过人工复核保证质量。

下一步我们可以用一周时间做一份竞品分析样稿，验证 AI 是否能在竞品研究和策略洞察上真正节省时间。

## 10. 最终建议

不继续开发内容审核 Agent。

保留它作为 AI 研讨会项目成果：它证明了 AI 能做一部分基础检查，也帮助我们看清了模型在审核场景里的边界。

后续转向竞品分析报告。这个方向更符合现阶段模型能力，也更适合小组继续探索：用 AI 做资料收集、结构化整理和初步洞察，人负责判断、筛选和最终结论。
