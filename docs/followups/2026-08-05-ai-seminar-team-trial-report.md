# 内容审核 Agent 组内试用 Follow-up 报告

日期：2026-08-05  
项目：百度地图内容审核台 / 内容审核 Agent  
场景：AI 研讨会项目后续评估  

## 1. 背景

我们小组在 AI 研讨会中提交了“内容审核 Agent”项目，希望用 AI 辅助完成供应商稿件的预审、风险识别和问题沉淀。项目已经完成了一个可试用版本，支持团队成员登录、上传 Excel、批量审核、查看五维评审结果，并生成需要人工确认或供应商修改的任务。

这次 follow-up 的目的不是证明 Demo 能跑，而是基于组内真实试用反馈，判断这个项目是否值得继续投入，以及如果继续做，应该往哪个方向优化。

## 2. 当前结论

建议继续开发，但不要把它定位成“自动替代人工审核”的工具。更合理的方向是：

> 面向内部内容审核的 AI 辅助工作台，帮助审核同学更快完成批量预审、风险定位、人工复核分流和供应商问题沉淀。

这轮测试说明方向是有价值的：系统确实能把 Excel 稿件批量跑起来，也能输出五个维度的审核意见。但它目前还没有达到稳定日常使用的程度，尤其是在审核口径、产品事实理解、错误提示和团队协作流程上还需要一轮集中优化。

如果后续只看“能不能完全自动审核”，这个项目会显得不够成熟；但如果把目标调整为“减少人工初筛时间，提高问题定位效率”，它仍然值得继续做一版内部 MVP。

## 3. 本轮试用结果概览

已经跑通的能力：

- 团队成员可以登录系统。
- 成员可以填写自己的 One API key 和模型配置。
- 可以上传 Excel 稿件并生成批次。
- 可以对批次进行 AI 审核。
- 审核后可以看到五个维度的结果：基础内容校对、合规审核、品牌一致性、产品准确性、传播有效性。
- 系统会给出发布状态，例如通过、需要人工确认、需要修改、暂不可发布。
- 内容表中可以看到每条稿件的状态、风险和任务数量。

组内测试中暴露的问题也比较集中：

- 有同事访问本地服务时打不开。
- 有同事配置模型后没有拿到有效审核结果。
- API key 保存后，用户不确定是否真的生效。
- 有些 Excel 行因为标题为空或字段不完整，没有进入自动审核。
- 内容表里的“任务”列不够直观，用户不知道点哪里，也看不出具体要做什么。
- 审核规则对小红书标题党和口语化表达过于敏感。
- 产品功能事实库不完整，导致实际支持的能力被误判为需要人工确认。

## 4. 关键反馈与问题分析

### 4.1 审核条件偏死板，标题党表达被误判为风险

同事反馈：

> 一些问题其实只是标题党，为了吸引人眼球，但系统都算成了风险项。

典型例子：

- “现在出去玩儿再也不用费劲做攻略了”
- “下次追范丞丞线下再也不用做攻略了！”
- “怀疑小度想想在我脑子里装了监控”

这些表达在小红书、KOC 种草内容里很常见，很多时候是为了制造标题吸引力，并不一定是在做严格的产品承诺。比如“再也不用做攻略”如果正文只是描述一次厦门出游体验，那么它更像是个人体验的夸张表达，而不是“产品永久解决所有攻略问题”的承诺。

目前系统的问题是，它对“再也不用”“搞定所有”“监控”等词比较敏感，容易直接触发中风险判断。这样会带来两个后果：

- 误报偏多，审核人需要花时间解释“这其实只是标题党”。
- 供应商会觉得系统太机械，不符合平台内容语感。

建议优化方向：

- 审核时不要只看关键词，要结合正文判断标题是否被内容支撑。
- 把“标题修辞建议”和“真实合规风险”分开展示。
- 对小红书常见标题党表达建立白名单或低风险样例库。
- 如果表达只是轻微夸张，但正文有场景支撑，可以给“建议优化”而不是直接判中风险。

已经调整的规则方向：

- 新增“标题党/口语化吸引表达”的安全边界。
- 明确不能只因为出现“再也不用”“搞定”“神器”等词就直接判风险。
- 要区分“吸引眼球的标题钩子”和“产品能力/长期效果承诺”。

### 4.2 产品功能理解不够，实际支持的能力被转人工复审

同事反馈：

> 实际拥有的内容，审核觉得不能实现，需要人工复审。是不是可以加一个产品功能点的东西进去？这种小事儿可以直接审核，不需要再耗费人力。

典型例子：

- 稿件里写“直接帮我打个车吧”，系统判断为打车完整交互流程缺少已批准事实支持。
- 稿件里写“能切换同款语音”，系统判断为该语音能力不在已批准产品事实中。

这个问题不是模型本身“不聪明”，而是产品事实库不完整。系统只能根据当前标准包里的已批准能力来判断。如果打车能力、同款导航语音能力没有明确写进去，模型会倾向于保守处理，把它转成人工确认。

这说明项目如果要继续做，必须把“产品功能事实库”作为核心模块，而不是只靠一段 prompt 让模型自己判断。

建议优化方向：

- 建立产品功能白名单：明确哪些能力已经确认支持，可以直接通过。
- 建立灰名单：哪些能力部分支持，需要限定表达。
- 建立禁用口径：哪些表达当前不能说。
- 每次活动 brief 或产品更新后，可以由管理员补充功能点。
- 审核结果里展示“命中的产品事实依据”，让审核人知道系统为什么放行或拦截。

已经补充的能力方向：

- 支持用户用自然语言提出打车需求，并在用户确认后的打车流程中衔接出行方案。
- 支持在活动授权口径下切换或使用合作同款导航语音。
- 仍然不放开“无需确认即可自动完成打车”这类更强承诺，避免误审。

### 4.3 团队试用门槛偏高，非技术同事容易卡在配置阶段

这次试用中，登录、访问地址、API key、模型配置都出现过问题。对于开发者来说，这些问题可以通过看日志和改配置解决；但对于团队成员来说，它们就是“系统不好用”。

目前比较明显的问题：

- 本地服务依赖个人电脑和局域网 IP，同事不一定能稳定访问。
- API key 保存后不回显是安全的，但用户不知道是否生效。
- 模型不可用时，前端给出的解释不够直接。
- 如果 OneAPI 返回 503，用户看到的结果更像“审核失败”，但不知道原因是模型不可用。

建议优化方向：

- 部署到固定地址，不依赖个人电脑启动。
- 保存 key 后展示“已保存、已验证、上次验证时间”。
- 模型配置保存时先做一次连通性测试。
- 管理员能看到团队成员是否完成 key/model 配置。
- 模型不可用时，不生成内容风险结论，而是明确提示“系统异常，未完成审核”。

### 4.4 审核结果可解释性还不够

同事反馈中提到，任务表看不出修改情况，点击刚导入的内容也没有明显反应。这说明当前界面虽然有数据，但信息层级还不够清楚。

目前的问题：

- “1 个开放任务”太抽象，不知道是合规问题、产品问题还是文案建议。
- 点击区域不明确，用户不知道哪里可以看详情。
- 有些结果显示“需要人工确认”，但没有足够解释为什么必须人工确认。
- 系统异常、内容风险、产品事实缺失混在一起，容易造成误解。

建议优化方向：

- 任务列直接显示任务类型，例如“产品准确性需确认”“合规表达需修改”。
- 点击整行后自动跳到详情。
- 把“系统异常”和“内容风险”分开，不要让用户误以为模型不可用也是稿件问题。
- 每条审核结论都给出“依据来源”：来自合规规则、产品事实库、品牌口径，还是模型建议。

## 5. 是否继续开发：判断

### 值得继续做的原因

第一，它解决的是一个真实工作问题。团队确实有批量稿件预审、统一口径、供应商修改建议沉淀的需求。

第二，当前版本已经跑通了核心链路。虽然体验还粗糙，但从上传、审核到查看结果的主流程已经成立。

第三，这个项目的价值不只在“审一条稿”，更在于长期沉淀。随着产品事实库、合规规则、供应商常见问题不断积累，系统会越来越贴近团队真实口径。

第四，它适合作为 AI 研讨会后的延展项目。它不是单纯炫技，而是能落到一个具体业务流程里。

### 不建议继续走的方向

不建议把它包装成“全自动审核系统”。从这次试用看，内容审核里有很多边界判断：标题党、语境、活动授权、产品功能是否上线、表达是否过度承诺。这些都需要人和规则一起判断。

也不建议马上扩展更多新功能。当前最影响体验的不是功能少，而是几个基础问题还不稳：访问、配置、错误提示、事实库、结果解释。

如果下一阶段继续堆功能，系统会看起来更复杂，但不一定更好用。

## 6. 推荐下一阶段方向

建议把下一阶段目标收敛成一句话：

> 做成一个可靠的内部审核辅助 MVP，让 5 个团队成员可以独立完成上传、审核、查看问题、导出修改建议。

优先级建议如下。

### P0：让团队能稳定用起来

- 部署到固定地址。
- 保证前后端服务稳定运行。
- 固定团队账号和初始密码说明。
- 管理员可以查看成员配置状态。
- OneAPI key 和模型配置增加验证机制。

### P1：减少误报和无效人工复审

- 补充产品功能事实库。
- 增加标题党/平台语感样例。
- 区分“内容风险”和“表达优化建议”。
- 对已确认支持的产品能力直接放行或低风险通过。

### P2：提升审核结果可读性

- 任务列展示具体问题类型。
- 详情页展示命中的规则和产品事实依据。
- 报告页总结高频问题。
- 支持导出给供应商的修改清单。

### P3：沉淀成团队资产

- 建立供应商问题库。
- 建立可复用修改建议库。
- 建立产品功能白名单/灰名单/禁用口径。
- 每次活动结束后生成复盘报告。

## 7. 下一轮验证指标

建议再做一轮小规模验证，再决定是否继续投入更大资源。可以设定以下门槛：

- 至少 5 个团队成员能独立完成登录、配置 key、上传和审核。
- 至少 3 个真实批次、50 条以上稿件完成审核。
- 90% 以上稿件能得到有效审核结果，而不是系统异常或模型不可用。
- 审核人能看懂每条内容为什么通过、为什么修改、为什么人工确认。
- 误报问题明显下降，尤其是标题党和已支持产品能力相关误报。
- 审核同学主观认为它至少节省 30% 初筛时间。

如果这些指标达不到，就不建议继续做成完整平台，可以转向更轻量的方向：

- Excel 审核报告生成器。
- 供应商问题沉淀助手。
- 单篇稿件批注工具。
- 审核规则问答助手。

## 8. 给老板汇报时可以这样说

这次组内试用验证了项目方向有价值，但也暴露出它还不是稳定生产工具。

它现在最适合的定位不是“AI 自动替代审核”，而是“AI 帮审核同学做第一轮预审和问题归类”。它可以把批量稿件里的风险点、产品口径问题、需要供应商修改的内容先筛出来，让人工审核更快进入判断环节。

目前最需要补的是两件事：

第一，产品事实库。系统必须知道哪些能力是真的支持，哪些能力只能限定表达，哪些能力不能说。否则它会把很多实际支持的能力转成人工复审。

第二，平台语感。小红书内容里有很多标题党和夸张表达，不能只按关键词判断风险。系统需要理解标题、正文、产品能力之间的关系。

建议继续投入一个短周期，把它从 Demo 打磨成内部可试用 MVP。下一阶段不追求更多功能，而是优先解决稳定访问、模型配置、误报控制和结果解释。

## 9. 最终建议

建议继续开发一轮，但要收敛目标。

继续做的理由是：它确实能解决团队批量内容审核的初筛问题，也有机会沉淀产品口径和供应商问题库。

需要调整的是：不要把目标定成“全自动审核”，而是先做“AI 辅助审核工作台”。只要它能稳定减少人工初筛、减少重复判断、帮助团队沉淀问题，就已经具备继续投入的价值。

下一阶段建议用 1-2 周做可用性加固和审核口径优化。完成后再用真实批次复测一次，再决定是否扩大使用范围。
